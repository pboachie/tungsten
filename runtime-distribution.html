A successful local build does not mean a version exists in a registry. Before relying on registry installation, check the version required by your generated package. The available stable packages and candidate source routes are separate choices; installing a runtime does not install the Tungsten compiler.

The latest stable compiler release is 0.1.2. The three npm runtimes, PyPI tungsten-runtime, Maven Central Java runtime, NuGet C# runtime and RubyGems runtime were verified at 0.1.2 on October 15, 2026. These native packages were qualified with generated SDK consumers; their publication does not make the 0.1.3 compiler available. Compiler 0.1.3 remains unreleased: use matching source dependencies for its candidate capabilities, including Python 3.10/3.11 support and HTTP/Git input acquisition. The Go runtime is separately available as v0.1.3 through the public Go module proxy, which does not establish a stable 0.1.3 compiler release. Its archive includes the verified Apache-2.0 runtime license. The getting-started installation guide separates those published runtime commands from the candidate source workflow.

Neither Rust runtime package is available from crates.io in the October 15 registry checks. Use the v0.1.2 source checkout with the stable compiler, or the same reviewed candidate checkout with the unreleased compiler. Set the Rust target's runtime_path to runtimes/rust/runtime; a generated CLI also needs cli.kit_path pointing to runtimes/rust/cli-kit in that same checkout. Resolve runtime_path relative to the generated SDK crate directory and cli.kit_path relative to the generated CLI crate directory. Do not use cargo add registry commands until the required versions are published and verified separately. These libraries do not install the Tungsten compiler. Use the compiler's release binary/installer or its documented source installation separately.

Runtime source uses Apache-2.0; the generator's license is separate. Registry archive notices are verified separately from source and consumer builds. The qualified Go v0.1.3 archive includes the runtime's actual Apache-2.0 license. npm packages ship compiled ESM, TypeScript declarations and explicit exports. @elysra/tungsten-runtime/node supplies Node adapters; the core and WebMCP import graphs stay free of Node builtins. The MCP runtime runs on Node and can import Node functionality. Browser WebMCP API availability depends on the host browser and is checked separately from package distribution.

For candidate capabilities or runtimes without a published package, build the runtimes and set the generator's supported runtime path options to your local checkout. A source path is a development dependency; package releases use registry version ranges. Put runtime_path in the target's configuration, resolving it relative to its output directory. For example, a Java SDK emitted to sdk/java alongside a local tungsten checkout can use:

targets:
  java:
    out: sdk/java
    runtime_path: ../../../tungsten/runtimes/java

Use the corresponding runtimes/<language> directory for other source targets. Kotlin also needs the Java runtime path; F# also needs the C# runtime path. Keep those dependencies from the same reviewed source revision. The generated README may show registry-style coordinates or an example SDK install command; these identify the expected dependency, rather than promise a published package.

For the released 0.1.2 compiler, build the Go emitter from the v0.1.2 checkout and use that checkout's runtime source. Configure the Go target's runtime_path with the matching source directory:

targets:
  go:
    external: true
    out: generated/go
    module: example.com/my-api/sdk
    runtime_path: /absolute/path/to/tungsten-v0.1.2/runtimes/go

This stable source route does not require the 0.1.3 compiler or runtime. As with the other outputs, configure the external emitter before generation and follow the generated SDK's build instructions.

The candidate Go emitter defaults to the existing runtime module v0.1.3, available through the nested-module tag runtimes/go/v0.1.3. A root compiler release tag does not replace this module-specific tag. For the unreleased compiler's source workflow, use runtime_path with the same reviewed checkout. To explicitly evaluate the existing candidate module in an isolated consumer:

go get github.com/pboachie/tungsten/runtimes/go@v0.1.3

The generated SDK already declares that dependency. A clean Go consumer resolved it through the public module proxy and checksum database without runtime_path, a replace directive or a sibling source checkout. Set runtime_version to select another compatible published version, or use runtime_path for a local development replace. This Go publication does not establish registry availability for other languages.

The release checks also install all npm tarballs together into an isolated project, so the core peer is resolved from the packed artifact instead of a source link or an unpublished registry version.

The 0.1.3 source candidate coordinates compiler and runtime source versions for its planned release tag. Generated SDKs retain their own package versions, while their default runtime dependencies require the candidate's capabilities. Explicit runtime overrides remain yours to qualify. The Go module's independent nested tag and archive notices are verified separately from the compiler release. The earlier 0.1.2 release had independently versioned non-npm runtime sources. Local archive checks validate each manifest, and tag-aware release checks enforce the coordinated candidate versions. Neither replaces a clean registry installation check or proves publication.

Publication automation builds and checks registry archives separately from source generation. It verifies package versions, archive contents and digests, then checks public downloads after an approved release. Workflow configuration, local package checks and registry publication are separate checks. No unreleased 0.1.3 package is required for the stable 0.1.2 installation route.
