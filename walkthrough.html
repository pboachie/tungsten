What was checked

  • Kotlin and matching Java/Kotlin runtimes compiled for JVM 17. F# built with matching F#/C# runtimes for .NET 10. These two SDKs were build checked; their API calls were not exercised.
  • Dart was analyzed and AOT compiled, then its generated client performed a local GET with strict response validation. Dart uses dart:io; browser transport is not demonstrated.
  • HTTP and local Git inputs retained their source pins and caches. Offline checks passed with the original source unavailable. Git used a shorter temporary project path after a deep Windows path failed.
  • The Rust/Axum segment calls the tungsten_contract::source_axum library API. It parses supplied text, retains an unresolved dynamic route and reports runtime_complete: false. It does not execute an Axum application or offer an init-from-Rust CLI.
  • The saved-cURL-to-Kotlin attempt intentionally refuses the unsupported target with TG0705 and exit 4. Imported formats do not support every native OpenAPI target.
  • The dependency caches were warmed. Build times are not benchmarks, and the recording does not establish registry parity, production acceptance, authentication, retries or mutation behavior.

Contents

0:00 Tungsten version 0.1.3 is published. This walkthrough shows real commands, local fixtures, and the limits behind the new features.

Published v0.1.3 and what is new

0:12 This is the published release archive, checked against its checksum and the exact source tag. The new SDK targets are Kotlin, Dart and F#. Together with the existing targets, native OpenAPI now supports ten SDK languages, including external emitter Go.

0:30 The demonstrations use one declared, read-only pets contract and matching source runtimes. Generated files, compiler builds and actual calls are different checks. Nothing here uses production credentials or sends a write request to a real service.

Generate three SDKs and compile Kotlin

0:48 One native OpenAPI contract generates all three new SDKs. The output directories and compiler manifests are real. Kotlin is a thin language layer over the Java runtime. Its transport is blocking, and the generated package targets Java seventeen.

1:06 Here the Java runtime compiles with release seventeen, then the matching Kotlin runtime and generated client compile with the pinned Kotlin compiler. The jar contains the actual client and model classes. This is a build check, not a claim that every runtime feature was exercised.

Build F# with matching .NET source runtimes

1:26 F# uses the shared C# core through a language-native API. This generated project targets .NET 10. The build uses the matching tagged runtime projects, and keeps its artifacts outside the source checkout.

1:41 The command serializes compilation to avoid a shared-output file lock observed during preparation on this Windows host. The SDK build succeeds without changing generated code. This segment does not execute an API call or test persistence, authentication or retry behavior.

Analyze, compile and run the Dart client locally

2:01 Dart has a native dart I O transport, not a browser transport. First analyze the generated package, then compile a small consumer into an executable. Dependency downloads happened during preparation; these warmed build steps are not benchmarks.

2:18 The executable now calls the generated pets method against an explicitly local fixture. It receives a typed Pet and uses strict response validation. The response is fixture data from a real loopback request, not a claimed result from a production API.

Pinned HTTP input, refresh and offline reuse

2:38 The compiler can now acquire an entry document from HTTP or HTTPS. This local server exposes the same read-only contract. Initialization retains a content pin and verified cache. Refresh inputs is an explicit online review step.

2:56 Now stop the source server and run generation with offline and check. The command succeeds using the retained pin and cached document. Keep both the source lock and its cache. A pin makes the input reproducible; it does not prove the remote API is unchanged or safe.

Native Git acquisition and offline commit pins

3:15 Git acquisition is now native to the compiler. This deterministic example uses a local Git fixture, a selected tag and one document path. Tungsten records the resolved commit and content hashes. The release also accepts the documented Git plus HTTPS form.

3:33 The earlier deep Windows project path failed, so this run uses a shorter temporary project directory. Temporarily make the source repository unavailable, then generate offline from its verified cache. The successful check demonstrates reuse without fetching or executing repository application code.

Bounded Rust/Axum library import

3:54 Rust and Axum support is a bounded library API, not an init from Rust command. The caller supplies source text, a router name and an explicit mount prefix. This real harness links tungsten contract from the exact release tag; it never runs the supplied application.

4:12 The literal typed route becomes candidate OpenAPI. The dynamic route stays unresolved in coverage. A separately saved origin override is preserved through inference. Runtime complete remains false: parsing selected declarations cannot establish runtime routing, authentication, macro expansion or application-wide coverage.

Policy limits and reproducible review artifacts

4:39 The new languages do not make every imported format eligible for every target. This saved curl to Kotlin attempt is an intentional refusal check. Version 0.1.3 rejects the unsupported target early with diagnostic TG0705.

4:58 Finish by checking regeneration. The review package retains real command exits, source pins, fixture inputs, dependency locks, captions and exact chapter times. This video establishes the checks shown, not registry availability or universal target parity. Human review comes before any publication.
