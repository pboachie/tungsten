# tungsten-mcp (experimental)

A native Python Model Context Protocol (MCP) server runtime for APIs generated by
[Tungsten](https://github.com/pboachie/tungsten). It serves the tools of a Tungsten MCP
manifest over stdio or Streamable HTTP on top of the generated Python SDK, so a server needs neither Node
nor a generated TypeScript SDK.

**Experimental, unreleased 0.2.0.** The package is not published. Its scope is the first
slices of [#154](https://github.com/pboachie/tungsten/issues/154): discrete and progressive
tools over stdio and Streamable HTTP. The TypeScript runtime (`@elysra/tungsten-mcp`, the `mcp` target) remains the
supported MCP server. See [Limits](#limits) before you use it.

## Generate and run a server

Add the `python` and `mcp-python` targets to `tungsten.yml`:

```yaml
targets:
  python: { out: generated/python }
  mcp-python: { out: generated/mcp-python }
```

Run `tungsten generate`, then install the generated SDK, this runtime and the generated
server into one environment (until the packages are published, from local paths):

```sh
pip install ./runtimes/python ./runtimes/mcp-python ./generated/python ./generated/mcp-python
```

The generated package's README names its command (`<api>-mcp`) and its environment:
`<API>_BASE_URL`, one variable per credential, `<API>_MCP_DEADLINE_MS` and
`<API>_MCP_MODE`. Configure your MCP client to launch the command; it speaks MCP on
standard input and output and writes its own errors to standard error.

## What it serves

- **Discrete mode.** The manifest's tools, one per operation and macro, with the same
  names, input schemas, annotations and output schemas as the TypeScript server. The
  output schemas are widened for the verification result, the redaction marker and the
  error envelope.
- **Progressive mode.** `search_tools` (BM25 over the manifest's index, optionally within
  one cluster), `describe_tool` (the schemas, tier, reserved fields, remediation table and
  an example call), `invoke`, `invoke_read` (read-only tools only), `preview` by name and
  `list_clusters`. Each result of `invoke`, `invoke_read` and `preview` names the tool it
  ran, its tier and its hints in `_meta["tungsten/tool"]`. The mode is the manifest's
  (`agent.yml` `disclosure.mode`, or `auto`), unless `<API>_MCP_MODE` overrides it.
- **Hints.** A tool's MCP annotations are never less cautious than its safety tier,
  whatever the manifest says.
- **Previews and confirmation.** When any tool is not read-only, `preview` renders the
  request and its effects without sending it. For a destructive or irreversible tool,
  `preview` also returns a `confirmation_token` bound to those exact arguments, in this
  session only. Only that string confirms a call: `true` never does
  (`allow_confirm_true` is off).
- **Results.** A success is the response body as `structuredContent` (a non-object body as
  `{value}`) and its compact JSON as text. Results are cut to `max_result_chars` (default
  50,000), arrays first and then strings, with a note. Every failure is a tool result
  with `isError: true`, the diagnostic envelope verbatim as `structuredContent`, and its
  remediation as text. These failures are never protocol errors.
- **Deadlines.** `tool_deadline_ms` (`<API>_MCP_DEADLINE_MS`) is passed to the client
  runtime as each call's `deadline_ms`. It bounds authentication, idempotency-key
  reservation, queue admission, every attempt, retry waits, response bodies,
  verification and a whole macro. When it expires, the result has `code: DEADLINE_EXCEEDED`
  and nothing more is sent. A mutation that was already sent reports `OUTCOME_UNKNOWN`,
  which is a different category: retry it only with the same idempotency key.
- **Runtime policy.** Every call goes through the Python runtime: argument validation,
  safety tiers, idempotency keys, safe retries, verification of irreversible operations,
  imported-operation policy and response bounds (`max_response_bytes`, default 4 MiB).
  Sensitive response fields and shown-once results are returned once per session. An
  identical replay gets them redacted.
- **Binary bodies.** A binary request body is accepted as base64 (standard or base64url)
  text and sent as bytes.

## Limits

- **Streamable HTTP.** `--http <port> [--host <host>] [--token-env <NAME>]` serves
  `http://<host>:<port>/mcp` through the SDK's session manager, with one tool session (its
  own API client, confirmation tokens and shown-once state) per `Mcp-Session-Id`, closed
  when the SDK drops the session. Every request is checked first, with the TypeScript
  server's rules:
  1. the bearer token, compared in constant time; otherwise 401;
  2. the path; otherwise 404;
  3. the Host header (loopback names, or `allowed_hosts`, when the server is bound to
     loopback or `allowed_hosts` is set); otherwise 403;
  4. the Origin header (loopback origins or `allowed_origins`); otherwise 403.
  The defaults are 64 sessions, a 4 MiB request body and a 30-minute idle timeout
  (`HttpOptions`). Binding a non-loopback host with no token and no allowed hosts prints a
  warning. Legacy HTTP+SSE is not served, and there is no OAuth resource-server
  integration: use a bearer token or your own access control in front.
- **Sessions without an id.** A request that carries no `Mcp-Session-Id`, from a
  stateless client, gets a fresh API client. A confirmation token therefore does not outlive
  that request, and destructive calls cannot be confirmed without a session.
- **Search is keyword only.** The embedding (hybrid) search of the TypeScript server is not
  served; `search_tools` ranks with BM25 alone.
- **Streamed results.** A tool whose operation answers an event stream collects its events
  in order: at most 1,000 (then `truncated: true`), at most `max_stream_bytes` of JSON
  (default 4 MiB) and at most `max_stream_ms` (default 60 s). Past a limit the call fails
  with an `UNEXPECTED_RESPONSE` envelope and the events collected so far as `partial`.
  The deadline bounds connecting and reconnects, and these limits bound collecting.
  Progress notifications are not sent.
- **No `run_script`.** Unrestricted Python evaluation is never offered.
- **No embedding search, resources, prompts or server-to-client features.**
- **Macros** run only when the generated Python SDK emits them (see its TG0730
  diagnostics). A macro tool it cannot run answers a "misconfigured" envelope and sends
  nothing.
- **Protocol.** It is built on the official MCP Python SDK, pinned to `mcp==2.3.0`. That
  release negotiates protocol revisions `2024-11-05` through `2026-07-28` and serves both
  the handshake and the per-request protocol eras. Python 3.12 or newer is required.
- **Cancellation.** A client's `notifications/cancelled` cancels the call's task. When a
  request was already in flight, its envelope (`OUTCOME_UNKNOWN` for a mutation) goes to
  the client runtime's `on_diagnostic`, because the client gets no result.

## Programmatic use

```python
from tungsten_mcp import ServerOptions, load_manifest, run

options = ServerOptions(
    manifest=load_manifest("petstore_mcp"),
    create_core=lambda: AsyncPetstoreClient(ClientOptions(base_url=...)).core,
    name="petstore-mcp",
    version="0.1.0",
    tool_deadline_ms=30_000,
)
raise SystemExit(run(options))
```
