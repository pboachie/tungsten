# @elysra/tungsten-mcp

The Model Context Protocol (MCP) server runtime for APIs generated by [Tungsten](https://github.com/pboachie/tungsten).

Expose a generated API over stdio or Streamable HTTP. The runtime supports discrete tools, progressive discovery and search, previews and confirmation, per-session client state, structured results and sensitive-field redaction. An optional `run_script` sandbox supports bounded multi-call workflows.

## Install

```sh
npm install @elysra/tungsten-mcp @elysra/tungsten-runtime
```

Requires Node.js 22 or newer. This is an ES module package with TypeScript declarations. The core runtime is a peer dependency. The MCP SDK and QuickJS implementation are installed as dependencies.

## Generate and run a server

Install the [Tungsten CLI](https://github.com/pboachie/tungsten#install) and initialize your OpenAPI project:

```sh
tungsten init --from openapi.json --targets typescript,mcp
tungsten check
tungsten generate
```

Review the target package names and output paths in `tungsten.yml`, and the operation policies in `agent.yml`. Build the generated TypeScript SDK first. Then install and build the generated MCP package, configuring its SDK dependency for your published SDK or local checkout.

From the generated MCP package directory:

```sh
npm install
npm run build
npm start -- --stdio
```

Configure your MCP client to launch `node` with the generated package's absolute `dist/server.js` path. The generated entry point also accepts `--http <port>` and serves Streamable HTTP at `/mcp`; it binds to `127.0.0.1` by default.

## Programmatic integration

Use the generated API descriptors and MCP manifest when embedding the server in your own Node application:

```ts
import { ClientCore } from "@elysra/tungsten-runtime";
import { createTungstenMcpServer, loadManifest } from "@elysra/tungsten-mcp";
import { api, operations } from "./generated/typescript/src/descriptors.js";

const server = createTungstenMcpServer({
  name: "example-api",
  version: "1.0.0",
  manifest: loadManifest("./generated/mcp/manifest.json"),
  createCore: () => new ClientCore(api, {
    baseUrl: "https://api.example.com",
    operations,
  }),
});

await server.connectStdio();
```

Adjust paths to your generated outputs. `createCore` creates a separate client for each MCP session, keeping confirmation tokens and shown-once state scoped to that session. For manifests containing macros, also pass the generated macro descriptors in the `macros` option; the generated server entry point wires them automatically.

## Disclosure and safety

- Discrete mode exposes individual tools. Progressive mode exposes discovery tools such as `search_tools`, `describe_tool`, `invoke` and `preview`, keeping the initial tool listing small.
- Generated metadata carries operation safety, idempotency and confirmation requirements. A preview is not execution; execution still needs the required argument-bound confirmation token.
- HTTP exposure and API authorization belong to your application. Put non-local HTTP listeners behind appropriate access control.
- `run_script` is disabled by default. Enabling it requires an explicit sandbox configuration; Deno execution also requires a Deno executable. The WASM engine runs in a worker thread of the server process with configured bounds. `sandbox.maxConcurrent` (`perSession`, default 4; `global`, default 16) caps scripts running at once.
- Deno limits wall time and V8 heap on all platforms; its additional process data limit is enforced on Linux. On Windows and macOS, `memoryMb` does not bound memory outside the V8 heap, including `ArrayBuffer` backing stores.
