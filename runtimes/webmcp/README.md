# @elysra/tungsten-webmcp

The browser WebMCP adapter for APIs generated by [Tungsten](https://github.com/pboachie/tungsten).

Register page-scoped tools backed by a generated TypeScript SDK. Importing this package registers nothing: your application chooses when tools become available, which tools are exposed and when they are removed.

## Install

```sh
npm install @elysra/tungsten-webmcp @elysra/tungsten-runtime
```

This is an ES module package with TypeScript declarations. Its root import graph is browser-safe. The core runtime is a peer dependency.

WebMCP is experimental and availability varies by browser. The adapter supports the current `document.modelContext` contract and a structural adapter for legacy `navigator.modelContext`. Detect support before registering tools.

## Generate a browser adapter

Install the [Tungsten CLI](https://github.com/pboachie/tungsten#install), then initialize your OpenAPI project:

```sh
tungsten init --from openapi.json --targets webmcp
tungsten check
tungsten generate
```

The WebMCP target includes a linked TypeScript SDK target. Review output paths and package names in `tungsten.yml`, and operation safety in `agent.yml`. Install and build the generated SDK first, then the generated WebMCP package. For local development, configure `sdk_path` to the generated SDK directory.

In your frontend, import the generated adapter's built entry point:

```ts
import { detectWebMcpBackend } from "@elysra/tungsten-webmcp";
import { register } from "./generated/webmcp/dist/index.js";

const backend = detectWebMcpBackend();
if (backend) {
  const registration = await register({
    backend,
    client: {
      baseUrl: "https://api.example.com",
      fetch: (input, init) => fetch(input, { ...init, credentials: "include" }),
    },
  });

  window.addEventListener("pagehide", () => {
    void registration.dispose();
  }, { once: true });
}
```

Adjust the import path and base URL to your application. Keep the registration alive while the page needs its tools, then dispose it during navigation or component teardown. For a single-page application, also dispose it in your framework's route or component cleanup handler.

## Scope tools to the active page

Registration defaults to read-only operations. Use an explicit `allowlist` of manifest tool names to expose mutations or macros. Confirmation-requiring operations also expose preview tools; their executions still require the SDK's argument-bound confirmation token.

For route-based loading, use `createWebMcpRegistrationController` with dynamically imported generated `groups/<moduleKey>` entries. Each group exports `createScope`; `controller.replace` replaces the active scope and cancels superseded loads. Call `clear` when leaving a scope and `dispose` when the controller is no longer needed.

For lower-level integration, `registerTungstenWebMcp` accepts a `ClientCore`, a generated manifest and registration options. An abort signal cancels active calls and removes owned tools. Streaming and binary results require explicit bounded collection or rendering policies.

## Browser authorization

Use your application's browser session and API authorization. The API must enforce access controls; tool annotations do not grant access. Configure CORS and CSRF protections for your deployment, and keep server credentials out of frontend bundles. Keep the separate `@elysra/tungsten-runtime/node` export out of browser code.

## Limits

Browser support depends on the available WebMCP backend. No file-backed OAuth token store is provided; persist credentials only through application-owned browser authorization flows.
