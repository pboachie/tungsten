# Contributing to tungsten

Thank you for your interest in tungsten, an agent-native SDK generator and MCP
compiler written in Rust. Contributions of all sizes are welcome: bug reports,
specification edge cases, and patches.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Security problems are reported privately; see [SECURITY.md](SECURITY.md).

## Start with an issue

Please open an issue before writing a large patch, so that the approach can be
agreed before you invest the time. Small fixes (typos, obvious bugs) can go
straight to a pull request.

- Bug reports: use the bug report form and include the tungsten version, the
  smallest OpenAPI snippet that reproduces the problem, the command you ran and
  what you expected compared to what happened.
- Feature requests: use the feature request form and describe the problem
  before the solution.

## Building

You need the Rust toolchain pinned in `rust-toolchain.toml`; `rustup` installs
it automatically on the first `cargo` invocation.

```sh
cargo build
./target/debug/tungsten check path/to/openapi.json
```

Before sending a pull request, run the same checks CI runs:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
python3 .github/scripts/repository_guard.py --repo . --range origin/main HEAD
```

The runtimes under `runtimes/` (TypeScript, Python, Rust and the MCP runtime)
have their own toolchains; build the one you changed.

## Licensing

tungsten uses a licence split, and your contribution is licensed accordingly:

- The compiler (`crates/`) is AGPL-3.0-only. Every Rust source file there starts
  with `// SPDX-License-Identifier: AGPL-3.0-only`.
- The runtime libraries that generated SDKs depend on (`runtimes/`) are
  Apache-2.0. Every source file there starts with
  `// SPDX-License-Identifier: Apache-2.0` (`#` for Python).
- Code generated by tungsten is not covered by the AGPL and carries no licence
  from tungsten. The owner of the API description chooses its licence.

A Developer Certificate of Origin sign-off is not required. By opening a pull
request you confirm that you wrote the change or have the right to submit it
under the licence of the files it touches.

## Tests are maintained privately

This repository holds source code and the standard community files only. The
test suite, conformance corpus, golden files and design documents live in a
separate private repository, so pull requests here must not add tests, test
data, `#[cfg(test)]` modules, `[dev-dependencies]`, doctests or documentation
directories. A repository guard job in CI enforces this. Besides the community
files at the root and in `.github/`, only images in `assets/` and code in
`examples/` (with the `examples/README.md` gallery index and a `README.md` per
example), and package READMEs directly in the runtime package directories
(including `runtimes/rust/runtime` and `runtimes/rust/cli-kit`) are accepted.

You do not need access to that suite. A maintainer runs it against your pull
request, and its result appears on the pull request as the `tungsten-ops/ci`
status. If it fails, a maintainer will share what is needed to fix it. If your
change needs new test coverage, describe the scenario in the pull request and a
maintainer will add it.

## Pull requests

- Submit your PR without needing to choose a release or apply labels. A
  maintainer assigns its intended release using a `release:X.Y.Z` label and
  updates that label if plans change. You may suggest a target in the PR
  description; the label is a plan, not a promise that the change has shipped.
- Release planning, version bumps and publication are coordinated by the
  maintainer. Only @pboachie creates release tags and publishes releases.
- Keep a pull request to one logical change, and link the issue it addresses.
- Follow the existing style; `cargo fmt` and clippy must be clean.
- Intermediate representation changes must be additive.
- Update `CHANGELOG.md` under `Unreleased` for user-visible changes.
- From 0.1.3 onward, compiler and runtime package versions follow the release
  tag in lockstep. One release preparation change updates their manifests,
  lockfiles and runtime identity headers together; ordinary feature changes
  leave versions alone. `node .github/scripts/check-release-version.mjs
  --workspace` checks source consistency, and the release prepare job checks
  the tag before building. Generated SDK package versions remain user-owned.
- Behaviour of the TypeScript, Python and Rust runtimes must stay identical;
  a behavioural change in one is made in all three.

### Releases and tags

Before a release tag is pushed, the release workflow is run once on the exact
release commit through `workflow_dispatch` with `dry_run: true` (the default).
The dry run exercises the same pipeline as the release — the dependency
advisory audit, the full build matrix, the SBOM and the crates.io, npm and
PyPI publish dry runs — while publishing nothing, so advisory matches and
packaging failures surface before an immutable tag exists. A release whose
dry run has not passed on that commit is not tagged.

Release tags are immutable. Once a `vX.Y.Z` tag has been pushed it is never
moved, re-pointed, or deleted and re-created: build provenance attestations,
the release job's `--verify-tag` check and everyone who fetched the first
commit all key on that exact tag. A failed release is fixed forward with a
new version and a new tag, never by moving the published one.

### Commit messages

- Write a short imperative title and, if useful, a body explaining why.
- Do not add AI attribution to commits: no `Co-Authored-By` trailers naming an
  AI assistant, no session links and no "generated with" footers. CI rejects
  them. Using tools to help you is fine; you remain the author and are
  responsible for the change.
- A DCO `Signed-off-by` line is not required.
- Keep commit messages and changelog entries suitable for public release notes.
  Do not include references to the private repository (issue, pull-request,
  commit or discussion links and `#` references), internal planning paths,
  release-plan or release-evidence paths or operational runbook paths. Describe the public behavior
  instead; CI rejects these references.

## Review

Reviews are done by the maintainers listed in
[`.github/CODEOWNERS`](.github/CODEOWNERS). Expect a first response within a
week; ping the pull request if it has been quiet longer.
