Case study: the ZROtext pilot

ZROtext is an open-source Android SMS gateway with a Rust server. Its contract is three OpenAPI 3.1 documents (the public, sealed and workflow planes, 44 operations in all), and it ships hand-written clients, which makes it a useful baseline. It was the first real API tungsten was pointed at: the TypeScript, Python and Rust SDKs, the generated CLI and the MCP server were generated from those documents and two manifests, then every scenario was run against a live instance on loopback. Nothing in the pilot sends a real SMS. This page summarises what the run showed. The generator now also provides SDK guides for TypeScript, Python, Rust, Go, Java, Kotlin, C#, F#, Ruby and Dart; the historical pilot results below cover only the targets actually exercised in that run.

Live rerun (2026-10-15)

The release-branch source SDKs passed all 27 live scenarios in TypeScript, Python sync, Python async, Rust, Go, Java, C# and Ruby: 216 scenario runs, 114 steps and 80 server-observed requests per driver. No driver or scenario was skipped. The cross-runtime check matched all 27 scenarios in each of seven comparisons with TypeScript. The generated Rust CLI passed 20/20 checks.

This run used an isolated PostgreSQL database and a native pinned server, synthetic accounts/devices, a loopback recording fault proxy and disabled external dispatch. It covers source builds of the SDKs and CLI against the currently approved upstream snapshot. The newer upstream snapshot still needs regeneration and regression qualification; this baseline does not establish acceptance against that snapshot, registry installation or a deployed service. The original historical results above retain their original scope.

Headline

  • The generated TypeScript, Python (sync and async) and Rust SDKs pass all 26 live scenarios against the real server: 4 driver runs, 104 scenario runs.
  • The parity check finds the four records identical (26/26, three times). The generated Rust CLI passes 20/20 live checks.
  • All the live scenarios pass in every SDK and in the CLI.
  • No runtime or emitter defect was found. The live run found four defects in the agent manifest; all are fixed with offline regression tests, and one led to the new tungsten check warning TG0614.
  • ZROtext's hand-written alpha clients behave the same on the wire but give their caller only status, code and Retry-After.

Findings

Each finding has a fix and an offline regression test, so the mock-based suite catches it next time.

  1. Reserved callback hosts. The server refuses callback hosts under .test, .example, .invalid, .local and similar suffixes with a 400 error; the example host and the mock both accept them. Fix: the agent.yml remediation text names the rule.
  2. Expiry window. An expiry more than 15 minutes ahead gets a bare 400 that the spec never explains. Fix: an operation-specific remediation with retryable: after_remediation.
  3. Ungated planes. The sealed plane's gate was declared but no sealed operation named it, and the workflow plane had no gate, so a default deployment's 404 came back as NOT_FOUND. Fix: a gate on all 15 sealed and 9 workflow operations, plus a gate for the workflow plane; new tungsten check warning TG0614 for a gates entry no operation uses.
  4. Rate-limit text. A rate-limit answer on submit carried the "four requests in flight" text when the live cause was the 60-per-minute budget, and had no same-key rule. Fix: an operation-specific remediation with same_key_only.
  5. Harness. Live runs were order dependent because of the server's budgets and caps (8 webhook endpoints, 16 pending messages per device, 60 submissions per minute). Fix: the proxy's reset restores server state before every scenario.
  6. Submit-key policy. At the live run, the manifest required a UUIDv4 submit key; the server accepts any 1–128 character [A-Za-z0-9._-] key. The SDK follow-up below brings the submit policy into line with that contract.

SDK follow-up (2026-10-12)

  • TypeScript, Python, Go and Rust SDK packages now include preserved custom webhook helpers for the pinned ZROtext signature contract: exact raw body, canonical timestamp and lowercase signature, five-minute default tolerance, constant-time HMAC verification, and strict signing-secret decoding. Event-ID deduplication remains the receiver's responsibility.
  • The TypeScript SDK includes the upstream profile-02 outbound composer and verified-manifest authorization chain as custom extensions, with HPKE pinned in the target manifest. The production API uses fresh random key material and returns exact envelope bytes and the unsigned digest. Retain and resend the same bytes after uncertainty. This matches the handwritten TypeScript composer; Python, Go and Rust continue to accept externally composed bytes.
  • Alpha submit and its macro accept the server's 1–128 ASCII token contract (ascii_token_128), including non-UUID keys. Webhook replay still requires UUIDv4. Caller ownership, preview tokens, secret handling and the no-retry policy for mutations remain intact.
